# Робота 1. Три предметні мови

## 1. Макромова World of Warcraft

**Задача й користувач:** гравець у бою повинен миттєво реагувати, поєднуючи кілька дій в одну кнопку залежно від ситуації.

**Що спрощує:** короткі команди (`/cast`, `/use`) з умовами в квадратних дужках дозволяють описати просту розгалужену логіку (чи триває бій, чи затиснута клавіша, яка обрана ціль). Це власна мова клієнта гри з фіксованою граматикою — не Lua і не інший інтерпретатор загального призначення, тому вивчати повноцінну мову програмування чи API не потрібно.

**Де межа:** немає циклів, змінних і довільного коду — лише наперед визначений набір команд і умов, і це обмеження свідоме: Blizzard навмисно не дає виконувати повний Lua-код у бою, щоб не можна було автоматизувати ротацію. Повноцінна логіка зі станом доступна тільки на рівні аддонів, які пишуться вже на Lua з XML для інтерфейсу.

## 2. Нотація кидків кубиків у настільних рольових іграх

**Задача й користувач:** гравцю чи ведучому потрібно швидко й однозначно записати випадковий результат дії.

**Що спрощує:** короткий запис типу `1d20+5` одразу передає, скільки кубиків кидати, якої грані, який модифікатор додати і чи брати кращий/гірший з двох кидків — без словесних пояснень механіки.

**Де межа:** нотація нічого не каже про те, що робити з отриманим числом — інтерпретація результату (успіх, шкода, ефект) залишається логікою самих правил гри, а не запису кидка.

## 3. JQL (Jira Query Language)

**Задача й користувач:** користувачу системи керування задачами потрібно знайти конкретний набір задач за проєктом, статусом, виконавцем чи спринтом.

**Що спрощує:** мова оперує поняттями, звичними для трекера задач, і має готові функції («поточний користувач», «активний спринт»), тоді як звичайний SQL до внутрішньої бази вимагав би складніших запитів із з'єднанням кількох таблиць.

**Де межа:** мова вміє лише читати дані за наявною моделлю задач — не можна ні змінювати дані, ні виходити за межі цієї моделі, тож для складнішої звітності (наприклад, зведених таблиць) доводиться переходити до звичайного програмування поверх API.

## Git — теж предметна мова

**Задача й користувач:** Git зберігає історію змін у проєкті: видно, хто, що й коли змінив, і можна повернутися до будь-якої версії. Ним користуються розробники та всі, хто працює з файлами в команді.

**Що спрощує:** кожен працює у своїй гілці, а потім зміни зливаються докупи, і не треба пересилати файли на кшталт `final_v2_точно_останній`. Кілька коротких команд (`add`, `commit`, `push`), і зміни вже на GitHub.

**Де межа:** Git погано підходить для великих бінарних файлів, як-от відео чи проєктів Photoshop: він не бачить, що саме в них змінилося, а репозиторій швидко роздувається. Паролі й ключі туди класти не можна, бо з історії їх так просто не прибереш.
